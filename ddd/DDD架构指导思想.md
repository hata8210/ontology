在项目架构设计中，DDD（Domain-Driven Design，领域驱动设计） 是一种以业务业务逻辑（Domain）为核心的软件架构设计方法论。它由软件大师 Eric Evans 在 2003 年提出，旨在解决大型复杂业务系统的失控问题。
DDD 的核心思想是：代码的结构应当直接反映业务的真实运作方式。它不急于设计数据库表，而是先理清业务概念。
DDD 的设计思路通常分为两个层面：战略设计（Strategic Design）和战术设计（Tactical Design）。
------------------------------
## 一、 战略设计（高层俯瞰：画业务地图）
战略设计关注的是系统的大局观和业务边界，解决的是“系统如何拆分”的问题。
## 1. 统一语言 (Ubiquitous Language)

* 核心思想：开发人员、业务专家（产品经理、运营等）必须使用同一套名词来沟通并写进代码中。
* 目的：消除沟通鸿沟。如果产品经理叫“用户”，运营叫“会员”，代码里写 Account，系统就会走向混乱。在 DDD 中，这个词必须统一（例如统一为 Customer）。

## 2. 子域 (Subdomain)

* 把庞大的业务根据重要性和功能拆分成不同的子域：
* 核心域 (Core Domain)：企业的核心竞争力，最赚钱、最需要花精力自研的部分（如电商的“交易系统”）。
   * 支撑域 (Supporting Subdomain)：核心域需要的周边业务，不可或缺但非核心（如“商品库存系统”）。
   * 通用域 (Generic Subdomain)：市面上已有成熟解决方案的通用功能（如“认证授权”、“短信通知”）。

## 3. 界限上下文 (Bounded Context)

* 核心思想：给概念划定边界。在这个边界内，一个名词的含义是唯一且确定的。
* 举例：Product（商品）这个词。在“商品上下文中”，它包含图片、详情、规格；在“仓储上下文中”，它只关心长、宽、高和重量；在“财务上下文中”，它只关心成本和税率。DDD 主张不要建立一个万能的 Product 大对象，而是在不同的界限上下文中各自建立专用的对象。

------------------------------
## 二、 战术设计（微观落地：代码结构）
战术设计关注的是界限上下文内部的代码如何组织，提供了一套构建块（Building Blocks）。

+-------------------------------------------------------------+

|                     聚合根 (Aggregate Root)                  |
|                                                             |
|   +-------------------+              +------------------+   |
|   |   实体 (Entity)    | <--------->  |  值对象 (Value)  |   |
|   |  (有唯一标识 ID)    |              | (无标识/只读/属性) |   |
|   +-------------------+              +------------------+   |
+-------------------------------------------------------------+
                              ^
                              | (管理生命周期)
                     +-----------------+

                     | 仓储 (Repository)|
                     +-----------------+

## 1. 实体 (Entity)

* 特征：具有唯一标识（ID），且在其生命周期中状态会发生改变。
* 举例：User（用户）。即使两个用户的名字、年龄完全一样，只要 ID 不同，他们就是两个不同的人；用户的密码变了，但他依然是同一个人。

## 2. 值对象 (Value Object)

* 特征：没有 ID，不可变（Read-only），纯粹用来描述属性。只要属性值相同，两个值对象就是等价的。
* 举例：Address（地址）。“北京市朝阳区XX路”是一个值对象。如果用户改了地址，不是去修改原地址对象的属性，而是直接用一个新的 Address 对象整体替换掉旧的。

## 3. 聚合与聚合根 (Aggregate & Aggregate Root)

* 核心思想：将紧密关联的实体和值对象组合成一个聚合。
* 聚合根：是这个聚合的唯一外部代言人。外部系统只能通过聚合根来访问或修改聚合内部的数据，从而保证数据一致性（不变量）。
* 举例：Order（订单）是聚合根，OrderItem（订单商品明细）是内部的实体。你绝不能跳过 Order 去直接修改 OrderItem 的价格，必须通过 Order.updateItemPrice() 来触发，由订单统一计算总价和优惠。

## 4. 领域服务 (Domain Service)

* 特征：当某个业务逻辑不属于任何一个特定的实体或值对象，或者涉及多个聚合之间的协作时，就应该将其抽离为领域服务。
* 举例：TransferService（转账服务）。转账涉及“A账户（聚合）”和“B账户（聚合）”，把转账逻辑写在任何一个账户里都不合适，此时需要一个领域服务来协调。

## 5. 仓储 (Repository)

* 特征：负责聚合根的持久化（保存和读取）。它是一个接口，隐藏了底层数据库（MySQL/MongoDB等）的细节。
* 区别：传统的 DAO（Data Access Object）针对的是数据库表；而 Repository 针对的是整个聚合。

------------------------------
## 三、 DDD 架构分层模型（四层架构）
在传统的 MVC 三层架构中，业务逻辑经常被写在 Service 中，导致 Service 臃肿，变成“贫血模型”。DDD 引入了四层架构（或六边形架构/洋葱架构），将领域逻辑解耦：

   1. 用户接口层 (User Interface / Adaptor)：处理 HTTP 请求、RPC 调用，进行参数校验（DTO 转换），不含业务逻辑。
   2. 应用层 (Application Layer)：很薄的一层。不包含核心业务逻辑。它像一个编排者（导演），负责开启事务、调用领域服务或聚合根、调用邮件通知等。
   3. 领域层 (Domain Layer)：整个系统的核心（纯净的业务逻辑）。包含实体、值对象、聚合、领域服务。这一层不依赖任何底层技术框架（如 Spring/MyBatis/Database）。
   4. 基础设施层 (Infrastructure Layer)：提供通用的技术能力。如数据库实现（RepositoryImpl）、缓存、消息队列、日志等。

------------------------------
## 四、 为什么项目需要 DDD？（总结）

* 防止系统腐化：传统开发容易把业务代码写成“流水账（Transaction Script）”，最后谁也看不懂。DDD 让业务逻辑内聚在领域对象中（充血模型）。
* 天然适配微服务：DDD 的 界限上下文 (Bounded Context) 是微服务拆分的最佳理论依据。一个上下文往往就对应一个微服务。
* 高内聚低耦合：业务逻辑在领域层，不受数据库换型或框架升级的影响。
