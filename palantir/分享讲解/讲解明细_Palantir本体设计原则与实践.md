## 一句话定位
作者近期工作中大量做本体设计，研究并实践了 Palantir 本体设计方法论。本片分享**四项核心设计原则 + 四个关键结构设计模式 + 四个常见反例 + 行业最佳实践与避坑经验**，并强调"先跑起来再完善"的实用导向。

## 一、四项核心设计原则（按优先级）

### 1. 领域驱动设计（最重要）
- **基于业务领域建本体**，建模的是真实世界（真实实体/关系/规则），而不是基于原始数据直接建模。
- 正确三步顺序：**① 理解业务领域**（识别真实世界实体与关系，如客户属于哪个领域/产品线）→ **② 设计本体模型**（定义对象类型、属性、关系、接口）→ **③ 映射原始数据与逻辑**（可能是结构化/半结构化/非结构化数据）。
- **先从领域开始，再到模型，最后才碰数据**；不要"手头有什么数据就直接建模型"。
- 反例：拿一个 CSV 每列映射一个属性（订单号/客户名/邮箱/SKU 都塞进一个"订单数据"实体）——里面其实隐藏了**订单、客户、产品三个独立实体**；正确做法是用予余（Relation）连接（客户"拥有"订单、订单"含"产品）。
- 判断标准：建模完，用户或 AI agent **不需查文档、凭直觉**就能看懂"这是什么东西、业务含义是什么"。

### 2. 不要重复构建相似实体（Don't Repeat Yourself）
- **每个概念只保留一个规范化的表示**；给出"三次法则"：同一东西出现一次=巧合、两次=模式、三次=必须重构。
- **部门孤岛反例**：同一"Customer"，销售建了 CaseCustomer、支持建 SupportCustomer、财务建 BillingCustomer，各自都放 name/email/phone，结果同一客户有三条记录且信息不一致、三套 Action 各自维护。
- 两种修法：
  - 单一规范化类型：统一成一个 Customer，共享同一套属性（名字/邮箱/电话/生命周期）。
  - 若各部门定义**确有本质差异**：用**接口（Interface）**，定义 Customer-based 接口放公共属性（Name/Email/Phone），各部门 implement 接口 + 各自特殊字段扩展。

### 3. 开闭原则（对外扩展开放、修改关闭）
- 对已上生产的本体：**核心模型上线验证后即锁定，新需求通过"扩展"加入**，不要直接往核心 Object 里塞字段。
- **上帝对象反例**：Equipment 核心类型最初只有序列号、模型、Location 三个属性，被各团队不断加字段（认证/财务/维保），最终 150+ 属性、绝大多数每个对象都是空值，且任何人改核心类型都会破坏别人使用。
- 正确做法：核心 Equipment 保持 3 个字段不动；新需求通过**新类型 + 接口**扩展（如 EquipmentCertificate 单独建一张表/对象，建立接口来关联）。

### 4. 组合优于继承
- 多层继承链易"名越"——Asset→PhysicalAsset→Building 需要 4 层才能表示"可排期（可测）的建筑"。
- Palantir Foundry 接口支持**多重继承**，一个实体可以同时是 Building 也是 Resource：创建一个 Arena 对象，implement 了 Building + Resource 两个接口；这样构建一个"工作流"无需修改即可直接应用到 Arena——**通过组合/接口装配，而非逐层向下继承**。

## 二、四个关键结构设计模式（Palantir 的"子结构法则"）

1. **规范化（Normalize）**：每个事实只存一次，用**答辩属性**（derived property）提供便利访问。使联络：雇员汇报对象=5，不去 hardcode，而是让派生属性基于关系技术计算；Employee 也不用复制 ManageName，直接用链接、名字变了自动跟随。（注意超 1 万对象查询效率会变慢）
2. **结构体（Struct）**：把相关的字段打包成一个结构。地址很多相关字段（Address Street、Address City 等）不要拆 10 个独立属性，用一个 Address 结构体封装，还能附带自信度/来源信息——对 AI 类型重要。
3. **接口（Interface）**：面向未来扩展的抽象。如 Vehicule/Equipment/Facility 都需要"可分磨性"，定义一个 Inspectable 接口，一次定义、多处实里现，工作流建在此接口上，新增类型无需改主体结构。
4. **对象化的链接（Object-backed link）**：关系本身带有元数据。如 Employee 和 Venture 之间不只是直线，用 VentureStaffing 耦合对象记录角色、投入比例、开始时间等——**既能保留直接链接的便利，又能承载完整的关系元数据。**

## 三、四个常见反例（独立维度）

1. **金锤子（使用 hammer）**：对单一工具的过度依赖——"手里只有锤子看什么都像钉子"：用什么都是用 action、所有计算都写 pipeline。应对：**按场景选工具**：需人工判断/用户输入→Action；批量转换/聚合→Pipeline；低延迟→Streaming pipeline，否则 batch；事件触发→Automation/事件驱动；跨对象复杂计算且输入随 action 变→Function 或派生属性；简单稳定输入→pipeline 预计算。
2. **操作碎片/动作蔓延（Doomen 化）**：为一个对象建 20 多个单属性 action（更新名/邮箱/电话）。应**合并成一个围绕"业务操作"的 action**（如 update employee），而不是把数据库操作直接暴露给用户。
3. **时间机过（Time Machine）**：把历史版本建模成独立对象类型——合同分 contract v1/v2/v3 变成不同实体，结果不知当前是哪个、链接该指向哪个。应合并成一个实体，**历史变更用链接类型记录**（如 contract + contractAmendment 字段存变更记录），否则类型会随变更次数爆炸增长。
4. **命名不当**：缩写/意思模糊/误导性命名（item、value 不明）会让理解不一致，是本体论构建最大技术债、后期修复代价高。对策：**标准化、能执之（product/sales/order）的一致命名**。

## 四、选工具：问哪些问题（展开自拍）

- 需人工判断/用户输入 → Action；
- 路径：转换/聚合 → Pipeline（低延迟用 Streaming，否则 Batch）；
- 事件触发 → Automation（事件驱动、监听变化编排下一步）；
- 跨对象复杂计算、输入会随 action 变 → Function 或派生属性；
- 简单且输入稳定 → Pipeline Precompute。

## 五、行业实践五条补充经验（作者+行业权威）

1. **使用上层本体框架，改进**：领域已有成熟本体框架，如金融领域的 FIBO（Financial Industry Business Ontology）、Geometric、BFO（Basic Formal Ontology）等通用概念可借用，直接辅助构建（呼应之前 LLM 驱动构建中的"框架派"）。
2. **语义提升**：从业务流程图、UML、BPMN 等模型，通过语义标注转成本体实体与关系。
3. **治理与经营**：每个实体、属性明确 Owner/所属人/Sponsor，并配数据管家（data steward）等角色——做到"谁负责、谁管理、谁背书"，同前数据中台对表的负责人管理。
4. **实体分类框架（实际件的分类）**：分三类——**业务实体**（客户/产品/设备，直接业务建模）、**过程实体**（如巡检、审批、预警，在业务流程中产生的动作）、**结果实体**（如风险报告、推荐方案、风险结论等"人工产出"）建立后可查、可追溯、可推送。新建类型先反问：它是直接业务实体、过程实体，还是计算出来的结果实体？
5. **集中式定义 + 分布式填充**：本体可通过"定义权"集中、保持一致性（数据血缘连贯、同字段命名一致），业务在数据扩展过程中集中填充，与企业数据治理逻辑一致，与覆一一前文"对扩展开放"原则一致。

## 结论：最后必记住的原则（实用主义）

**在实际使用中产生价值的一个小缺陷的本体，远胜于在书桌里完美的理论模型。**不要一开始就设计一个完美模型——先通过小步快跑（迭代）让本体支撑业务运行、支撑 AI 理解业务，把事情跑起来，再逐步叠加完善。
