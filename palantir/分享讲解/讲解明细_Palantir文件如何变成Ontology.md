## 一句话定位

本片回答 **"企业里一堆文档、表格、PDF 等不同来源的文件，是怎么一步一步变成 Ontology（本体）的"**——这是很少人完整讲的"脏活累活"（Dirty Work），也是 Ontology 企业落地中很大一部分工作。作者用 Palantir 官方文档的**航空公司场景**把整个链路完整走一遍。

## 三类输入数据（航空公司数字化负责人视角）

1. **结构化数据**：航班运营数据（CSV / Database），来自 Oracle、Metabase 等数据库；字段如航班号、出发时间、状态、飞机尾号。
2. **半结构化数据**：乘客预定数据（JSON 格式），来自 OTA 订票系统，结构嵌套复杂（乘客信息 + 多段行程）。
3. **非结构化数据**：维修工程师手写的 PDF 扫描件维修记录，完全没有数字化结构。

## 整体五阶段链路

1. **数据连接（Connect）**：把数据源「原封不动」拉进来，**不做任何预处理**——这是 Palantir 的第一原则，所有变化都在 Foundry 内部完成，才能从本体任意点追溯到原始文件（金融/医疗等合规严格行业是硬性要求）。
   - Connect 方式：Find 里含 200+ 连接器，支持文件、PDF、视频、图片等格式。
   - 拉取方式两种：**Snapshot**（每次全量替换）| **Append**（只追加新数据），对增量更新很关键。

5. **存储（Store）**：两个关键数据。
   - **DataSet**：通用存储容器（CSV/JSON 等），带版本记录，被称为"Git for Data"，任何历史版本可找回。
   - **MediaSet**：专为图片、视频、音频、PDF 设计，在 DataSet 基础上增加与 AI 提取工作流的接口。
   - **MediaReference** 设计：DataSet 某一列可直接引用 MediaSet 里的文件（如维修记录每一行指向原始 PDF 扫描件），把结构化与非结构化关联起来。

6. **解析/清洗（Transform）**：听三类数据走三条路。
   - 结构化 CSV：用 Foundry 的 **Apply Schema** 自动推断数据类型（时间/数字/文字），再拖拽式 Pipeline Builder 做过滤和去重，得到干净的 clean 表。
   - JSON/半结构化：**摊平嵌套**，核心操作 **Explode（炸开）**——把嵌套数据拆成独立行，一份订单（含两段行程）变成乘客表+预订表，用订单 ID 关联。
   - PDF/非结构化：必须让 AI 读。产品 **AIP Document Intelligence**，五步为：① PDF 进 MediaSet → ② OCR + 视觉理解 LLM 输出 Markdown（可用 Microsoft/开源 Markdown 库）→ ③ 从 Markdown 解析业务数据（尾号、维修日期、换件）→ ④ **校验核对**（含人工：格式、AI 置信度、随机抽样本对照原始 PDF；不要省略，最易出错）→ ⑤ 输出干净的 clean 维修表，每行保留指向原始 PDF 的一列以便追溯兜底。

7. **映射为 Ontology（Mapping）**：
   - 干净的表 → 一个 **Object Type**；表里每一**行** → 一个 **Object Entity（实例）**；每一**列** → 一个 **属性（Property），对应某实例的某个属性字段**。
   - 表间的关联关系 → **Link Type**（如 Flight 航班通过尾号关联 Aircraft）。
   - 数据读写操作 → **Action Type**（如改签、更新状态）——这是 Ontology 的核心创新，让业务用户能直接改数据，改动写入独立数据集，不污染原始数据。

8. **用起来（活用）**：还需要两样东西真正值钱：
   - **Logic**：逻辑计算与自动推导（如航班延误分钟：从出发/实际起飞自动算出；平均延误可跨航班聚合）。
   - **Action**：由四部分构成——①参数（需要哪些数据）②规则（执行什么）③前置条件（何时可执行）④副作用（执行后触发什么）；所有修改写入独立数据集，全程可追溯。

## 增量更新：不要全量重建

- 比喻：图书馆（2000 万本 = 历史数据），每周只更新新增的 100 万本（相当于新航班），避免全量重算浪费时间。
- 三层配合：①数据同步只拉新数据 → ②Pipeline 只处理新增行 → ③Ontology 只更新有变化的关联对象。
- 两个易踩的坑：
  - 状态被修改（准点→延误）时若用 Append 追加，会用现金出现新旧版本，需要在 Pipeline 里**去重（只保留最新）**。
  - 用户在 Ontology 里点改签是**立刻生效**，而 Pipeline 批量为定时跑，两组有**时间差**；Ontology 会自动合并但需注意时机（还有一个"时间差窗口"问题）。

## 关于宽表与 FDE（为什么 Palantir 有 FDE）

- 现实是 ERP 导出的往往是**几百列的"大宽表"**（订单/客户/商品/物流全堆在一起）。
- **Palantir 硬性规则：一个 Object Type（实际一个实体类型）只能对应一张表**，所以宽表不能直接映射，必须**拆表**。
- 在 Pipeline 里拆成几张小表（订单表/商品表/物流表），各自映射对应 Object Type，用 Link 关联。
- Pipeline Builder 有 AI 功能帮写拆分代码，但**决定怎么拆、哪个列属于哪一实体，仍需人为判断**——这是纯粹的业务场景建模，也正是 **Palantir FDE（现场部署/业务建模工程师）最贵的那部分时间**。
- 模板沉淀：技术上可行（把不同行业/业务域的模板沉淀、下次快速迭代部署），但 Palantir 没有动力去做——FDE 常驻咨询是他们的商业模式，也是绑定客户的核心资源。
- **真正的机会**：不再定义实体本身（供应链、SKU、医疗等行业打磨都高），而是当客户抛出如 SAP 大宽表时，制定**哪些列设到哪些实体、把 Mapping 规则产品化**——垂直行业玩家比 Palantir 更愿意做这件事。

## Palantir Ontology 与普通数据库 Schema 的真正差别（三点）

1. **全链路可溯源**：Ontology 任意一个字段/值都可追溯到原始文件的某一——对金融、医疗、政府/偏管/情报等合规严格行业是入场前提。
2. **可写回（反向）**：通过 Action Types 直接改、修改写到独立数据集，不污染原始数据。
3. **应用层直接消费**：无需再包一层 API，AI 和应用直接操作 Ontology 对象，一次操作完成——基于这些支撑在逻辑决策、业务决策等方面。

**结论**：这三点把它变成一个 **Agent 操作层，而非只一个数据结构目录。**
