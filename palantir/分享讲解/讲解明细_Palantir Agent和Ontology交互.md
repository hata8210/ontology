## 一句话结论
在 Palantir 体系里，Agent **不直接访问底层数据库表，也不自由扫描完整的 Ontology schema**，而是在一个**配置好的、受数据权限约束**的范围内，通过 Ontology 提供的**对象、关系、上下文、函数、动作**与企业业务交互。
通俗理解：**Ontology 是企业业务世界里受治理的语义接口，Agent 是通过自然语言使用这套接口的操作员；Ontology 就是 Agent 的操作系统（Agent OS）。**

## 前置：Ontology 到底是什么
很多人一听就以为它是知识图谱或数据结构，其实它是 **Operational Layer（操作层）**——位于数据库 / 表模型之上，把底层技术资产翻译成业务语言的层。Palantir 官方把它的能力分两类：
- **Semantic Elements（语义元素，描述世界）**：如 Supplier、Warehouse（仓库）、Customer 等 Object Type；Status、ETA、Priority 等属性；以及 Relation/Link（如 Order 属于 Customer）——解决“Agent 怎么知道企业里有什么、谁跟谁相关”。
- **Kinetic Elements（动能元素，改变世界）**：分两类：**Actions**（动态更新预估到达时间等，本质是函数形式的动作）与 **Functions**（纯函数，做计算：检查环节风险、优化调度）。

一句话：Palantir Ontology 的核心不是把表改名为“本体”，而是把企业的**名词、关系、规则、动作、权限**全部放进**受管控的语义层**。

## Agent 与 Ontology 交互的五层架构（本片核心主轴）

### 第 1 层 · Context Layer（上下文准备）
- 每次发消息，系统**自动**准备好背景上下文（确定性触发，无需 LLM 自行判断要不要查）。
- 三种准备方式：
  1. **Ontology context**：从对象类型里检索，可绑定固定对象（如华南仓库的库存、面积、负责人）；可用语义搜索（如“华南仓有无冷链断链投诉”）。
  2. **Document context**：从文档里按“全文 / 片段”模式捞取（如合同条款）。
  3. **Function-backed context**：高频企业检索场景里写一个函数，把客户/供应商等聚合成综合信息再给 LLM（比喻：秘书打电话汇总各部门情报）。
- 类比：秘书在老板进会议室前，把所有相关文档放到桌上。

### 第 2 层 · Query(Tool) Layer（主动探索）
- 与 Context 自动不同，这层由 LLM **自行判断**需要查什么、主动去查：支持**过滤、聚合、沿链接逐层渗透**。
- 关键区别：它查询的是 **Target（对象与关系）**，执行的是企业对象（订单、承运商、仓库等），而不是直接写 SQL 面对“表/字段”。
- 三种典型查询模式：
  1. 多条件过滤 + 聚合（如“今日华南区延误的高优先级订单”先筛选再计数，可追问“哪些是 VIP 客户”，沿 Order→HttpServer→Customer 关系继续过滤）。
  2. 沿关系链 budget（如订单 8832 延误在哪环节，沿 Order→Carrier 逐层，看一站式节点指标，得出如“维修+拥堵”）—像侦探沿着线索链追查。
  3. 聚合运营概览（按区域聚合，输出“红绿灯”看板）。
- **Context 与 Query 的分工原则**：必然知道的信息（当前仓库、今日 KPI、权限等级）放 Context；临时想探索的（让 Agent 自己判断）放 Query。Context 塞太多会 Token 浪费、噪声干扰、需更强上下文模型；Query 太窄又查不到、模型易自编。

### 第 3 层 · Logic Layer（业务逻辑）
- 查到对象后，Agent **调用封装好的业务函数**，而不是让 LLM 自己算。
- 例：用户问“这批军工订单风险等级”，会用 `CalculateDelay` 风险函数：查过去 90 天同路线数据、调天气 API、跑预测模型，输出“高风险，原因是仓库异常 + 目的地暴雨”。
- 原则：LM 负责理解意图、选择合适的函数、用自然语言解释；专业计算、规则、模型交给 Function，**不要让 LLM 直接凭空做专业判断**。

### 第 4 层 · Action Layer（执行动作）
- 让 Agent 从“问答助手”升级为“业务操作员”，对 Ontology 做受控的变更。
- 两种场景：**高风险操作**（如更换承运商）需用户确认（“B 单价比 A 高 12%、运费 +340 元，但时效提升 10%，是否执行？”）；**低风险操作**自动（如天气原因延误自动更新 ETA、自动通知客户）。
- 三个辅助工具：update context（改应用状态）、commands（触发其他应用，如在地图上标出某些订单）、request clarification（执行前向用户澄清模糊指令，避免不可逆错误）。

### 第 5 层 · Trust / Guard / Guard · Layer（护栏）
- “重头戏”：不是单层，而是**贯穿前面四层**的全局约束机制（权限、审计、安全边界）。
- 示例：同一运营助手，一线**调度员** vs **区域经理**看到、能做的完全不同：调度员只注入三条线路的 summary、可自动开 ETA、能算环节风险但不能算利润、不能分配承运商；区域经理则可查到华南全区绩效、可查利润、优化分配。
- **防幻觉的关键机制（企业最看重）**：不是简单警告“不要编造”，而是**从架构上让你“接触不到”**：
  1. 没有相应的 context → 看不到基准；
  2. 没有 financial-report object type0 → 检索不到；
  3. 没有财务权限 / 财务函数 → 算不了。
  三层叠加，Agent 对营收数据**完全不知情**，最终只能回复“我没有权限访问财务数据”，且**所有操作都进审计**（谁、何时、做了什么、结果如何）。

## 工具如何暴露给 Agent（两种模式）
- **Prompt tool calling**：把工具说明写进（system）prompt，几乎所有模型都支持。
- **Native tool calling**：用模型原生工具调用能力，可并行调用多个 tool。
- 易误解：Palantir **不是把完整 Ontology schema 全塞进 System Prompt**，而是只把当前 session（上下文被 page / 被授权）的那部分带进来。

## 端到端例子（串联）
用户问“帮我看看今年华南区有哪些订单有延误风险”：
1. Context Layer 自动：系统确定式触发，返回 top10 最相关的 summary 注入 LLM；
2. Query Layer：过滤华南区 + 延误，挑出订单/客户/当前等级；
3. 调用（Logic）函数算延误风险，并调用 App 方法给出一套建议（Resolution）；
4. LLM 汇总，询问“是否执行”；
5. 用户确认 → 派给承运商、创建异常单，元数据更新的同时 schema；全程由护栏层审计。

## 内部 Agent 与外部 Agent（接入）
- 前面的五层讲**内部 Agent** 与本体交互。外部 Agent 接入有两个机制：
  - **Palantir MCP**（面向开发者）：可改 Ontology 类型定义，但不能直接写数据。
  - **Ontology MCP / 外部业务 Agent**：能读数据、执行 Action 写数据，但不能改 Object Type 定义。
- 无论哪条路，**Agent 都只通过“受本单位接口访问一切，绝不绕过 Ontology 直接碰底层数据**。

## 作者落地了一个最小可工作版本（MVP 思路）
设计包含若干核心模块（九个核心主线、最小单元），可按此思路去构建一个最小版 Ontology + Agent 交互系统。

## 作者 Django Demo 演示
- 流程：导入 Ontology → 配置模型 → 对话。
- 本体配置：内置物流、采购等示例 Ontology（延续作者之前“LLM 构建本体”系列的视频）。
- 模型配置：可添加不同 LLM（含 DeepSeek 等）。
- 角色/权限管理：不同角色可配置不同权限（即 Guard 层）。
- 对话演示：问“现在有哪些订单有风险”→ 返回 12 个订单并标出高风险集合（延误评分 100%）→ 针对几紧急单给建议：
  - 建议砍掉延误，换承运商，模拟对比“延误时长缩短多少、额外成本增加多少”的替换方案，并建议主动与客户沟通。
  - 提供**推理可追溯**：展示 Agent 在过程中调用的工具（上下文注入 → Query 检索 Customer/Order 等对象 → 调用函数 → 返回结果）。
- 演示想表达：Ontology 让 Agent 不只是问答助手，而是能真正**查询数据、调用业务函数、做决策验证与模拟**，帮业务把“数据 + 逻辑 + 决策”串起来。
