## 开场：为什么需要 Ontology

- 反例：把公司文档直接丢给 LLM 让 AI 答"供应商 A 评分多少"，每次答案都不一样（85、92、78）——**AI 没有在说谎，只是不知道"供应商评分、日期"之间的关系**，每次都在做数据模仿。
- **Ontology = 知识地图**：不仅告诉 AI 有哪些数据，还告诉它数据之间**有什么关系、遵守什么规则**；有了地图，AI 才能从"随机猜测"变成"有据可查、跟随业务流程"。

## 传统构建方式的痛点

- 传统做法：知识工程师/业务专家花几个月在白板上画，写标准格式定义；建完业务又变了——**又慢、又贵、没人持续维护**，最终变成"死项目"/失效系统。

## LLM 构建 Ontology 的四道坎

1. **不知道有多少种类型**：一个领域事先不知道有多少实体类型（是 10 种还是 1000 种）。
2. **幻觉**：LLM 可能创造数据里根本没有的概念，当成事实。
3. **粒度难题**：关系太宽泛没用、太细没人维护……什么样的粒度才合适，很难把握。
4. **没有标准答案**：Ontology 没有对错，怎么评估好坏、能不能用都是难题。

## 五种流派（LLM 建本体的五种应对方式）

### ① 拆解派（可靠性最高）
- 把一个大任务拆成小任务，一步一步：**提取实体 → 提取关系 → 去重归一 → 双验证 → 建图**。
- 核心设计：**验证闭环**——每个新事实先通过"结构化检查 + 逻辑检查"才能进可信图谱，通不过只保留日志、不污染整个本体。
- 好坏例子：法国电力 EDF 用该方法管理核电站技术文档；缺点是工程量非常大，前一步出错会连带污染。
- 适用：要上生产系统、不容错时最可靠。

### ② 聚类派（让数据说话）
- 先别急着定义，把文档中的**名词**提取出来，用**聚类**（如 AP 聚类，不用 K-Means，因为提前不知道要聚几类），再用 LLM 为每一类取名。
- 代表论文：**2025 年 "LLM for Ontology"**——输入文档 → 提名词 → 用 **BERT 向量化** → AP 聚类 → LLM 小组名。
- 特点：数据驱动、拆小任务、幻觉分析低；缺点是聚类的质量直接影响最终结果；开放式（如 Wikipedia）数据下输出粒度可能过细。
- 适用：探索全新领域、不知道有什么类型时。

### ③ 两步走派（概念清单 → 层次结构）
- 先让 LLM 提取概念清单，再整理成有上下级关系的**层次结构**，最后序列化生成标准格式。先列提纲再组章节，中间过程可人工审查。
- 代表论文：**Onto-EKG**。
- 适合：快速输出 D 版验证想法。

### ④ 框架派（有标准先定框）
- **前提有已有框架**（如 **WikiData** 全球最大开放知识库，上亿实体），先定义好"可以有什么类型、什么关系"，让 LLM 在此框架内提取（不能乱发明）→ 减少幻觉，输出天然符合共识。
- 最适合医疗、法律、电力等行业（本身有标准 schema）。

### ⑤ 直给派（端到端、最快也最危险）
- 直接设计一个 prompt，让 LLM"从文本直接输出整个 Ontology"，一个人完成所有工作。
- 优点：最快，半小时可出结果；缺点：**幻觉风险最高、输出质量不稳定**，prompt 稍微一变整个 ontology 就变了（挑战赛也验证了这一点）。
- 适合：快速验证想法、学习理解 ontology、原型，**不是用在生产系统**。

## 流派选择判断框架

- 快速看 POC 方向 → **直给派**（LLM + prompt）。
- 探索全新领域不济 → **聚类派**（让数据告诉你）。
- 有行业标准和知识体系 → **框架派**（用 WikiData 或行业标准合规约束）。
- 要上生产系统不能出偏差 → **拆解派 +双重验证**（工程量虽大但最可靠）——这是"玩具 vs 生产系统"的分界线。

## 实战教训（重点）

1. **易错点在第一步 = 实体提取**：类型标错、关系错、别名混在一起 → 会一路传导、越攒越多，宁可在构建这步多吃功夫。
2. **garbage in garbage out**：如同数据治理，源数据脏，输出结果也会脏。
3. **prompt 措辞极其敏感**：换几个词结构就完全变化；用**结构化模板**而不是随手写自然语言，能大幅减少波动。
4. **并非数据越多越好**：有论文（如某篇 LLM-for-ontology 方法）用不足 1000 个 token 就建立有效知识图谱，关键在**数据的密度与约束的合理性**，而非数据量。

**一句话结论**：用 LLM 建 Ontology 不再是"能不能建"的问题，而是"怎么建更好"——五种方式各有适用场景，按需选择。

## 作者的开源工具演示（Ontoprompt）

- 基于"直给派 +一定约束 +抽取/验证规则"。
- 功能界面：概览、本体管理、提示词管理、模型管理、设置。
- 设置里可配 **LM 自信度阈值**（如 Action 最低自信度才提取）与验证规则（多文档已验证、本体质量验证）。
- **本体管理**：创建新 Ontology（选供应链领域 → 上传文件（支持多种类型：文档/Markdown/CSV）→ 配置 LLM（如供应链模板 + DeepSeek V4）→ 点开始提取 → 展示知识图谱：四大实体类型（Organization、Product、Document、Facility），可查看每个实体的属性、关联实体、关联逻辑规则（如采购触发、Action/动作）。
